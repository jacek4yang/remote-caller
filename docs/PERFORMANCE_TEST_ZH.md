# 性能与弱网测试方案

## 当前状态

代码具备弱网四档自适应，但在完成真实设备和受控网络测试前，不能把目标值当作已经取得的测试成绩。Chrome 开发者工具的普通 HTTP 限速不一定覆盖 WebRTC UDP；应使用 Linux `tc netem`、Apple Network Link Conditioner、专业网络仿真器或可控路由器。

## 网络矩阵

| 场景 | 下行/上行 | RTT | 丢包 | 抖动 | 预期 |
|---|---:|---:|---:|---:|---|
| 良好 Wi-Fi | 20M/10M | 40ms | 0.5% | 10ms | 1080p/60fps，稳定音频 |
| 普通移动网 | 8M/6M | 120ms | 2% | 30ms | 1080p/45fps |
| 弱网 | 2M/1.5M | 280ms | 5% | 60ms | 720p/24fps，音频连续 |
| 极弱网 | 1M/850K | 500ms | 10% | 100ms | 720p/15fps，压缩增强，语音优先 |
| 突发衰退 | 2M→200K→2M | 100–700ms | 0–15% | 120ms | 4–8 秒内降档，恢复后不反复震荡 |
| TURN/TCP | 500K | 350ms | 3% | 50ms | 能连接，延迟高于 TURN/UDP |

每个场景至少运行 20 分钟，iPhone Safari ↔ Android Chrome、Wi-Fi ↔ 5G、P2P ↔ TURN 分别测试；至少重复 5 次并报告 P50/P95，而不是只记录最好一次。

## 验收指标

- 建连时间：P95 直连小于 3 秒，TURN 小于 5 秒；
- 音频：48kHz 单声道 Opus VBR，上限 96Kbit/s（不含协议/中继开销），弱网不出现连续 1 秒以上静音；
- 视频：正常网络达到 1920×1080/60fps；极弱网目标仍不低于 1280×720/24fps，编码上限约 1.8Mbit/s；
- RTT：界面统计与 `webrtc-internals`/Safari Web Inspector 基本一致；
- 冻结：`freezeCount`、`totalFreezesDuration` 和最长冻结必须单独记录；
- 稳定性：连续 8 小时通话无进程崩溃、内存持续增长或 WebSocket 泄漏；
- 服务端：逐步压到每副本 5,000、10,000、20,000 空闲 WebSocket，记录 CPU、RSS、P95 信令转发延迟和重连成功率。

## 主观与客观画质

“人眼可见的清晰”应改成可重复验收：用预录人脸视频作为虚拟摄像头，在接收端录制，再计算 VMAF/SSIM；语音可使用 ViSQOL。真人测试同时评分面部轮廓、口型同步、声音可懂度和操作延迟。弱网档不追求高清纹理，而追求面部可辨识、口型基本连续和声音不中断。

## 进一步节流的取舍

- Opus DTX 可在双方安静时明显省流量，in-band FEC 能改善丢包但会增加少量冗余；应按真实丢包测试决定，而非一味追求最小字节数。
- AV1/VP9 在同质量下可能比 VP8/H.264 省码率，但旧款手机的软件编码会发热、耗电并增加延迟。生产应按双方能力协商，不应强制单一高复杂度编码器。
- 人脸裁剪、背景替换能减少画面熵，但会增加移动端 CPU/GPU 消耗；只有实测证明节省的码率大于耗电与延迟成本时才启用。
